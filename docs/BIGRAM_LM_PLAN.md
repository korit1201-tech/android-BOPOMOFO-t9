# Bigram 語言模型計畫（分支 `feat/bigram-lm`）

> 撰寫：2026-10-24，基準版本 v2.9.5。本文件記錄「為什麼做、參考了什麼、資料授權怎麼看、打算怎麼做、怎麼驗收」。
> 前身：`docs/ROADMAP_TODO.md` 的 A1。**動手前先讀「資料授權」一節。**

## 1. 為什麼做：實測結果

2026-10-24 用真引擎、真詞庫（`dict_tw.txt`）、九鍵、冷啟動（無個人化學習）跑 49 句日常語句（`tools/t9sim/sents.py` 的句子）：

| 指標 | 結果 |
|---|---|
| 整句一次打完，第 1 名正確 | 12 / 49（前 5 名也是 12） |
| 逐詞輸入，詞的第 1 名 / 前 5 名 | 157 / 214（73%） / 195 / 214（91%） |
| 一路接受第一名的字元正確率 | 266 / 334（80%）；不打聲調 257 / 334（77%） |
| 每次按鍵耗時（JVM） | 約 1.5 ms |

**全鍵盤基準（同日，`searchFullZhuyin`，同樣 49 句、真引擎、無個人化學習）：**

| 情境 | 整句第 1 名 | 逐詞第 1 名 | 逐詞前 5 名 | 貪心字元正確率 |
|---|---|---|---|---|
| 打聲調 | 21 / 49 | 197 / 214（92%） | 213 / 214 | 311 / 334（93%） |
| 不打聲調 | 15 / 49 | 136 / 214（64%） | 155 / 214 | 248 / 334（74%） |

「有上下文」與「完全沒有上下文」兩組結果**一模一樣**，代表目前那約 20 組手寫詞對對這份評測零貢獻。全鍵盤打聲調時只錯 17 個詞（14 個目標排第 2，都是同音字：做／作、哪裡／那裡、借書／結束、再／在、訂／定、得／的、想喝／很累／帶傘…），這類正是 bigram 擅長處理的；不打聲調時退步很多（92% → 64%），這是 bigram 預期效益最大的情境。

九鍵：答錯的 57 個詞：目標排第 2 名 24 個、第 3 名 10 個、第 4 名以後 19 個、完全沒出現 4 個。三種型態：
1. 常用功能詞被冷僻同音字壓過：「很」排在「系／係」後面、「要」在「有／藥」後面、「嗎」在「哪／那」後面、「吃」排第 34（「想吃」「喜歡吃」「一起吃」）。
2. 詞庫外的組合詞：「幫我」變成「不我」，「打給」「沒問題」「變冷」完全沒出現。
3. 同音字：做／作、在／再、的／得。

結論：缺的是**上下文排序**，不是覆蓋率（前 5 名涵蓋 91%）。

## 2. 現況：機制有，資料幾乎沒有

- 機制早就存在：`ZhuyinT9Engine.bigramMap` / `getBigramBoost` / `learnBigram`（v1.8.0，2026-09-26 起）；v2.6.0（2026-10-14）把它接進九鍵 DP、全鍵盤與實體鍵盤的整句組字（`currentContextWord`）。
- 但**內建資料只有約 20 組手寫詞對**（`initDefaultBigrams`，權重 500~800）加上使用者打字時學到的（每次 +500）。另有約 18 筆手寫的聯想詞 `defaultAssociations`。
- 所以這個專案要做的是「**補一份真正的 bigram 資料，並把它接上現有機制**」，不是從零寫新演算法。

## 5. 做法

1. **資料管線（放 `tools/`，依專案規定不進版控）**。來源 A：以本專案 `dict_tw.txt` 對 KeyKey 語料切詞（動態規劃，最大化詞頻）→ 統計詞對（以「含該詞對的文章數」為證據，文章內重複不放大）→ 只保留兩詞都在 `dict_tw.txt` 的詞對 → 依證據與 PMI 裁剪到預算內 → 輸出緊湊二進位 `app/src/main/assets/bigram_tw.bin`（排序鍵、量化權重）。來源 B：讀 `KeyKey.db` 的 `bigrams` 表，去掉讀音展開，詞對對應到本專案詞庫的詞，同樣輸出緊湊二進位。A、B 各產生一份，用同一份評測（含留出集）比較，也可試兩者合併。
2. **執行期**：延遲載入（背景執行緒，原子替換，沿用字典載入的架構）；`getBigramBoost` 先查內建模型、再加使用者學習層（現有 `bigramMap` 保留作個人化層）；找不到詞對時退回 unigram（不加分也不扣分）。
3. **保護機制**（借自 KeyKey）：高頻基本字的既有排序不得因 bigram 退步。
4. **預算**：APK 增量上限由專案擁有者決定（先前文件寫的 ≤ 3 MB 是前人規劃的估計，不是硬性需求；兩條路預期都在數 MB 內）；每鍵耗時增加 ≤ 20%；常駐記憶體增量要量測並記錄。

### 5.1 資料包獨立於 APK（2026-10-24 使用者決定採混合方案 C：APK 內建小核心包，另提供可下載的完整包，完整包在效能允許下可以較大）

bigram 資料不一定要打包進 APK，可以做成「資料包」另外下載，存在應用程式私有目錄（`filesDir`）：

- **混合做法（建議）**：APK 內建一份小的核心 bigram（約 2~3 MB，高頻詞對），離線第一天就能用；設定頁提供「下載完整詞對資料」，載入後引擎自動改用較大的那份。
- **主機與發布**：資料包放 GitHub Release 資產（`bigram_tw-vN.bin` + 含 SHA-256 的 `data-manifest.json`），並同步到 `/data/apk/`（`nas.korit.uk/apk/` 提供下載）；`deploy.py` 發版時一併處理。
- **安全**：下載後必須比對 SHA-256（雜湊值由 APK 內建或 manifest 簽署），驗證通過才以原子替換啟用；檔案標頭帶「格式版本」，與 APK 版本不相容時退回內建核心包。輸入法屬高信任元件，不可略過驗證。
- **備份**：資料包必須排除在自動備份之外（`backup_rules.xml`／`data_extraction_rules.xml` 加 `<exclude domain="file" path="...">`），自動備份上限約 25 MB 且沒有必要備份可重新下載的檔案。
- **隱私**：下載動作只在設定頁由使用者觸發，只抓取公開檔案、不送出任何輸入內容；README「純本地離線」的說法要改成「輸入內容完全不離開手機；可選擇下載資料包與檢查更新」。
- **好處**：APK 維持現在大小；詞對資料可以獨立更新，不必為了資料重新發版；可以提供不同大小的資料包。**代價**：多一套下載、驗證、版本相容與失敗回退的程式（約 1~2 天），以及離線且尚未下載時只有核心包可用。
- 載入方式用記憶體對應檔案（mmap）讀緊湊二進位，不用 SQLite，記憶體只佔實際讀到的頁面。

### 5.2 套用範圍（已讀碼確認）

三種模式都呼叫同一個 `getBigramBoost(prev, candidate)`：九鍵（`t9SegmentCost`、`t9ForwardPaths`、`t9PartialCandidates`、`t9MergeSentenceCandidates`）、全鍵盤（`searchFullZhuyin` 以 `× 500L` 加進權重、`getExactZhuyinWords`）、實體鍵盤（`findBestSentenceFromSyllables`）。換掉資料來源三種模式都會用到，但各自把加分併入分數的方式不同，**必須各模式分別校準與驗證**。使用者主要用九鍵與全鍵盤，實體鍵盤排後面。上下文詞 `lastCommittedWord` 在換輸入框、移動游標、換行時會被清空，句首第一個詞沒有上下文可用。

## 6. 驗收

- 既有 55 個單元測試全過。
- 以 49 句評測（見第 1 節）為回歸基準，**但不得針對它調參**：另切一份「留出集」，自語料依文章切分（訓練約 90%、驗證約 10%，兩者不得有相同文章或 20 字以上相同段落），並檢查 49 句本身沒有洩漏進訓練語料。
- 目標（估計，不是保證）：逐詞第 1 名由 73% 提升到 85% 以上；整句一次打完第 1 名由 12/49 明顯提高；任何基本字不得退步。
- 另用「輸入總動作數」（KeyKey 的 `TYPING_COST.md` 定義）作為補充指標。

## 7. 風險

- 語料是 AI 產生、偏書面且部分偏專業領域（生醫、旅遊、對話混合），與真實聊天分布有差距；後續可再產生口語對話語料補強，並與使用者個人化學習疊加。
- 語料裡有同音字寫法偏好（例如「過的」遠多於「過得」），bigram 不會自動解決所有同音字。
- 授權文字矛盾（見第 4 節）。


## 8. 進度與結果（2026-10-24，分支 `feat/bigram-lm`）

### 做了什麼
- `engine/BigramModel.kt`：讀 BGM1 格式（見檔頭註解）、64 位元 FNV-1a 雜湊鍵、依雜湊前 16 位元分桶的查詢（比整個 50 萬筆二分搜尋快），
  可退一步查「前詞最後一字 → 後詞第一字」的字元後備（實測沒有幫助，檔案裡預設不收，但程式保留）。
- `ZhuyinT9Engine`：新增 `getBigramBonus`（nat，取預先訓練模型與使用者學習的較大者，不重複計算）；九鍵的候選權重與整句成本、
  全鍵盤的單字同音字與精確詞排序、整句動態規劃都改用它；**全鍵盤的「單音節單字同音字」路徑原本完全沒用上下文，這次接上了**。
  背景載入：優先 `filesDir/bigram_full.bin`（日後的完整資料包），否則 `assets/bigram_core.bin`；任何失敗都退回沒有模型。
- 資料管線（`tools/bigram/`，依專案規定不進版控）：`common.py`（詞庫動態規劃切詞）、`build_pairs.py`（2,300 篇訓練文章的詞對，
  以「含該詞對的文章數」為證據）、`build_eval.py`（驗證集）、`build_model.py`（輸出模型檔）。
- 測試：`BigramModelTest`（7 個：跨語言雜湊、查詢、分桶、容錯）、`BigramBenchmarkTest`（正式評測，可用 `BENCH_CONFIGS` 掃參數）、
  資源 `bigram_eval.tsv`（600 子句、3,219 詞，取自與訓練完全分開的 130 篇驗證文章，0 句洩漏）。全部 61 個測試通過。

### 結果（600 句驗證集，冷啟動、無個人化學習；括號為相對 v2.9.5 的百分點）
| 情境 | 詞第 1 名 | 字元正確率 |
|---|---|---|
| 全鍵盤 不打聲調（主要用法） | 62.3% → **81.5%**（+19.2） | 74.4% → 86.8% |
| 全鍵盤 打聲調 | 85.8% → 89.5%（+3.7） | 89.9% → 92.5% |
| 九鍵 不打聲調鍵 | 59.9% → 68.3%（+8.4） | 68.2% → 74.4% |
| 九鍵 打聲調鍵 | 63.2% → 71.9%（+8.7） | 71.5% → 77.8% |
| 全鍵盤 整句一次打完（不打聲調） | 10.5% → 17.5%（+7.0） | — |

### 關鍵發現
1. **全鍵盤不打聲調的最大問題不是缺 bigram，而是一個 500 萬的固定加分**：沒打聲調符號時，所有「沒有聲調符號」的一聲字都被加 500 萬，
   遠大於任何詞頻，所以「我」排在「窩、渦、萵」後面、「和」排在「魽、憨、酣」後面。調成 3 萬（`fullNoToneFirstBonus`）：
   不用 bigram 就從 62.3% 到約 74%，加上 bigram 到 81.5%。取捨（出貨模型實測，不打聲調／打聲調）：500 萬 66.3%／89.8%、
   3 萬 81.5%／89.5%、0 82.8%／88.6%。會打聲調的人一聲字不寫符號，歸零會讓他們小退 1.2 個百分點；3 萬只退 0.4。
2. 「P(b) 用詞庫詞頻」的統計方式在所有情境都最好（加分 = 相對引擎已經給這個詞的分數額外多了多少）；折扣 0.5~0.9、上限 3~8 幾乎無差別；
   過濾弱關聯（最小加分 0.5、1.0）反而變差；字元後備沒有幫助。
3. 強度參數收斂在高原（全鍵盤 2~8、九鍵權重 3~10 結果幾乎相同），所以預設值不是精細調出的臨界點，穩定。
4. 九鍵剩下的錯誤多半是按鍵本身有歧義（剛／股／港／故、就是／幾乎），需要更多語料與更長的上下文，不是調參數能解。

### 成本
- APK：`bigram_core.bin` 4.34 MB（壓縮後約 4.06 MB，雜湊值幾乎不可壓縮）。debug APK 33.4 MB（未縮減）；v2.9.5 release 為 24.6 MB，預期 release 約增加 4 MB。
- 速度（JVM，每次查詢）：全鍵盤約 0.3~0.4 ms（原 0.3）；九鍵 3.8 ms（原 2.9~3.3，約 +15~29%，分桶前是 +46%）。**手機上的實際耗時尚未量測。**
- 若要再縮：格式 v2 把每筆從 9 位元組降到 5（桶號隱含 16 位元、剩餘只存 32 位元），可到約 2.8 MB，誤判率約 2e-9。

### 待決定／下一步
- 資料量其實只有 4.3 MB，**全部放進 APK 即可，「可下載完整資料包」的機制要等語料擴大後才有價值**（目前詞對只涵蓋驗證集 54%，語料不是飽和的）。`filesDir/bigram_full.bin` 的載入掛鉤與備份排除已就位。
- 一聲加分的預設（3 萬）是折衷；也可以做成設定項「全鍵盤：不打聲調／會打聲調」（0 對不打聲調的人多 1.3 個百分點，對打聲調的人多退 0.8）。
- 擴充語料（例如由 LLM 產生更多口語對話）、真機實測耗時與記憶體、手機上實際使用感受。
